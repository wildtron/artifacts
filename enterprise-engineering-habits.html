Enterprise Engineering Habits

Ten habits big teams use, scaled down so one person can run them on a homelab or a $6 server. Updated November 23, 2026.

Start here

This page builds on the Enterprise engineering habits page of the Clouds Against Humanity wiki (Apache-2.0). That project builds a small cloud lab with OpenTofu, Spacelift, DigitalOcean, Doppler and Twingate. The original names ten habits and says what each is for. This version adds four things to each habit:

  • A real incident where skipping the habit cost a company money, data or its existence.
  • Working configs you can copy: git hooks, CI workflows, nftables, systemd, SQL roles, restic and OpenTofu.
  • A check you can run that fails if the habit is not really in place.
  • Links to the sources, plus the control IDs auditors use, so you can talk to a security team in their own words.

It can look like a lot of ceremony for two small machines. That is the point. The habits are cheap when the system is small, and you will reach for them by reflex when it grows.

If you only do three

  1. Keep configs in git, with messages that say why. (Habit 1)
  2. Default deny. Nothing listens unless it has to. (Habit 4)
  3. Write down how to rebuild your most important box, then rebuild it from the document. (Habit 7)

Everything else is these three at a larger scale.

1. Everything is code, and code is reviewed

Nothing changes outside the repo. Every change, even one written by the only person on the project, goes through a pull request with checks and a description.

What it is for

Six months later, git log and the PR answer "why is this firewall rule here?" Without that record the rule is either feared or deleted. At 2am, "what changed?" takes one command, not an hour of guessing.

At home

Put compose files, /etc, router exports and Home Assistant YAML in git. One line per commit saying why, not what. The diff already says what.

Knight Capital, 1 August 2012. A new release was copied by hand to eight servers. One was missed. It still ran old code behind a reused flag, and in 45 minutes it sent millions of unwanted orders. The firm lost about $440 million and was sold months later. The SEC order says there was no written deploy procedure and no second person checking the deploy. One reviewed, automated deploy would have caught it.

Implementation

~/.gitmessage (then run git config --global commit.template ~/.gitmessage)

# Why (one line): what problem does this solve?

# What did you check, and how?

# Not verified:

.github/pull_request_template.md

## Why
## Change
## Testing
<!-- What you ran and what you saw. "Applied and checked `ss -tlnp`", not "tested". -->
## Not verified
<!-- Say what you did not check. An empty section means you checked everything. -->
## Rollback
<!-- A real step, e.g. "revert this PR and re-run the pipeline". "Restore from backup if needed" is not a step. -->

Branch protection: require a PR and one green check called "CI green"

gh api -X PUT repos/OWNER/REPO/branches/main/protection --input - <<'EOF'
{
  "required_status_checks": { "strict": true, "contexts": ["CI green"] },
  "enforce_admins": true,
  "required_pull_request_reviews": { "required_approving_review_count": 0 },
  "restrictions": null
}
EOF

For a server's /etc, etckeeper commits it to git for you, and commits again before and after every apt run:

sudo apt install etckeeper        # creates /etc/.git and the first commit
sudo etckeeper vcs log --oneline   # who changed what, and when
Check yourself. Pick any line in a config you run. Can you find, in under a minute, the commit that added it and the reason? Try git log -S 'the line' --oneline. Then try to push straight to main. It should be refused.

2. The thing that checks is not the thing that changes

The system that tests a change must not hold the keys to apply it. In the original project, GitHub Actions runs the tests and holds no cloud credentials. Spacelift applies changes and holds the write token. A human reads the plan and confirms it in between. A compromised tester can only block a change. It cannot make one.

Here the separation is between systems, not people. With one writer there is no human separation of duties, and the wiki says so. Separate systems still shrink what one bad dependency or one stolen token can do.

What it is for

CI runs code you did not write: every test framework, every package install script. If CI also holds the admin token, every one of those can reach production.

At home

The job that verifies your backups must not be able to delete them. Ransomware that gets your NAS should hit an append-only backup target it cannot wipe.

Code Spaces, June 2014. An attacker got into the company's AWS console and demanded money. When staff fought back, the attacker deleted servers, data and the backups, which lived in the same account under the same keys. The company shut down within days. One set of credentials could both run and destroy everything.
tj-actions/changed-files, March 2025 (CVE-2025-30066). A popular GitHub Action was changed to dump CI secrets into public build logs. Over 23,000 repos used it. Repos that kept cloud keys out of CI, or pinned the action by commit SHA, were not affected.
Try it: compromise one step of the pipeline
Attacker controlsHolds credentialsSkipped in this design

Implementation

.github/workflows/ci.yml: checks only, no cloud secrets anywhere

name: CI
on: [pull_request, push]
permissions: {}                 # start with nothing, add per job
jobs:
  checks:
    runs-on: ubuntu-latest
    permissions: { contents: read }
    steps:
      # Pin by full commit SHA, keep the version in a comment. A tag like @v4 can be moved.
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
        with: { persist-credentials: false }
      - run: tofu fmt -check -recursive
      - run: tofu init -backend=false && tofu validate
      - run: gitleaks detect --redact
  ci-green:                     # the single required check
    needs: [checks]
    if: always()
    runs-on: ubuntu-latest
    steps:
      - run: test "${{ needs.checks.result }}" = success

Applying happens elsewhere: a deploy service such as Spacelift, Atlantis or env0, or a separate GitHub environment with required reviewers, whose secrets only that one job can read.

Homelab: an append-only backup target with restic's rest-server

# On the backup box. Clients can add snapshots but never delete or rewrite them.
rest-server --path /srv/restic --append-only --private-repos

# On the NAS (the thing being backed up): it can only append.
restic -r rest:https://nas:SECRET@backup:8000/nas/ backup /srv/data

# Pruning runs ON the backup box, with local access, on its own schedule.
restic -r /srv/restic/nas forget --keep-daily 7 --keep-weekly 4 --prune
Check yourself. From the NAS, run restic forget --keep-last 1 against the backup repo. It must fail. Then grep -ri secret .github/workflows. Any cloud key that shows up there is a key CI can leak.

3. Least privilege, at every layer

Each credential and each process gets the smallest scope that still works. In the original project: the Doppler token reads one environment and cannot write, the first stage gets only the DigitalOcean token, a Twingate resource allows one host and one port, and CI starts with no permissions.

What it is for

You can't predict which part gets compromised. Least privilege decides how far it spreads: the blast radius. Ask of every part: if this is taken over, what can it reach?

At home

Dashboards get read-only tokens. The backup user can read the backup folder and nothing else. IoT gear sits on its own VLAN. Services run as their own users, not root.

Capital One, 2019. A misconfigured web firewall on AWS could be tricked into fetching the server's own role credentials (SSRF to the metadata service). That role could list and read hundreds of S3 buckets it never needed. About 106 million people's records were taken. A role scoped to the few buckets the firewall used would have exposed nothing.
Try it: blast radius on a homelab
Compromised or reachableControl path

Implementation

/etc/systemd/system/myapp.service.d/harden.conf: a service that can't touch the rest of the box

[Service]
DynamicUser=yes            # a throwaway user, created at start
NoNewPrivileges=yes
ProtectSystem=strict       # the whole filesystem is read-only...
ReadWritePaths=/var/lib/myapp   # ...except this
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
CapabilityBoundingSet=
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
SystemCallFilter=@system-service
systemctl daemon-reload && systemctl restart myapp
systemd-analyze security myapp   # scores exposure; aim for "OK" or better

PostgreSQL: a read-only role for dashboards

CREATE ROLE grafana_ro LOGIN PASSWORD 'change-me';
GRANT CONNECT ON DATABASE metrics TO grafana_ro;
GRANT USAGE ON SCHEMA public TO grafana_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO grafana_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO grafana_ro;

~/.ssh/authorized_keys on the backup host: this key can run one command and nothing else

restrict,command="/usr/local/bin/receive-backup" ssh-ed25519 AAAA... nas-backup
Check yourself. Log in as the dashboard role and run DELETE FROM some_table;. It must fail with "permission denied". SSH with the backup key and ask for a shell. You must get the backup command, not a prompt.

4. Default deny, and attach protection before the thing exists

Allow only what you need. Everything else is dropped. In the original project the cloud firewall has zero inbound rules and attaches by tag when the server is created, so there is never a window where a new server is open. Connectors dial out; nothing dials in.

What it is for

"Allow what you need" fails safe: a new service is closed until you open it. "Block what you don't want" fails open: every service you forget about is reachable. Internet scanners find a new open port within minutes.

At home

A Pi running one service should not have five other ports listening. Run ss -tulpn and justify every line.

Exposed databases, 2017 onward. Tens of thousands of MongoDB and Elasticsearch servers were left reachable with no password and no firewall. Attackers wiped them and left ransom notes. Most owners never meant them to be public. The software listened on all interfaces by default, and nothing blocked it.
Try it: scan a Raspberry Pi from the internet
Needed and allowedExposed by accidentBlockedClick a port to change its rule

Implementation

/etc/nftables.conf: drop by default, then allow the few things you need

#!/usr/sbin/nft -f
flush ruleset
table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;
    ct state established,related accept
    ct state invalid drop
    iif lo accept
    meta l4proto { icmp, ipv6-icmp } accept
    ip saddr 192.168.1.0/24 tcp dport 22 accept     # SSH from the LAN only
    tcp dport 443 accept                            # the one public service
  }
  chain forward { type filter hook forward priority 0; policy drop; }
  chain output  { type filter hook output priority 0; policy accept; }
}
sudo nft -c -f /etc/nftables.conf   # syntax check first
sudo systemctl enable --now nftables

Docker caveat. Ports published with -p 8080:80 go through Docker's own NAT rules and skip your host input chain. Bind to localhost or the LAN address: -p 127.0.0.1:8080:80, and put a reverse proxy in front.

Cloud: the firewall exists before the server, and attaches by tag (OpenTofu, DigitalOcean)

resource "digitalocean_firewall" "deny_in" {
  name = "baseline-deny-inbound"
  tags = ["managed"]            # any droplet created with this tag is covered from boot
  # No inbound_rule blocks at all: nothing gets in.
  outbound_rule {
    protocol              = "tcp"
    port_range            = "443"
    destination_addresses = ["0.0.0.0/0", "::/0"]
  }
  outbound_rule {
    protocol              = "udp"
    port_range            = "53"
    destination_addresses = ["0.0.0.0/0", "::/0"]
  }
}

resource "digitalocean_droplet" "connector" {
  name   = "access-tor1-connector-a"
  region = "tor1"
  size   = "s-1vcpu-1gb"
  image  = "ubuntu-24-04-x64"
  tags   = ["managed"]
}
Check yourself. From a machine outside your network (a phone hotspot works), run nmap -Pn -p- your.public.ip. Every open port it lists should match a line in your firewall config that you can explain.

5. Write the threat model down, including what you accept

List what you are protecting, what could go wrong, what stops it, and what you chose not to fix and why. The original project's threat model has seven assets, fourteen threats and a section of accepted risks, such as "connector tokens are readable from the metadata endpoint; accepted for now."

What it is for

A trade-off that is not written down looks like a mistake to the next reader, or to you in a year. A written model also tells you when it is out of date: any new component with credentials means a new row.

At home

Write the three worst things that could happen to your lab and what stops each one. If the answer is "nothing", that is next weekend's project.

The Threat Modeling Manifesto boils the whole method down to four questions: What are we working on? What can go wrong? What are we going to do about it? Did we do a good enough job?

Check yourself. Name the last thing you added to your lab. Is it in the table? Does anything in it hold a password or token? If yes and it has no row, the model is out of date.

6. Stage gates: small steps, each approved and costed

Build in numbered stages. Each one gets a design, a cost, an approval and an operator guide before it exists. In the original project, stage 1 did not start until stage 0 was built and checked. When the author rebuilt the cloud account, stage 0 found four surprises against the real API: a token missing a scope, a server size not offered in that region, a default VPC that could not be deleted, and a duplicate run. All four turned up where nothing was billing yet.

What it is for

When one thing changes and something breaks, you know the cause. When five things change at once, you don't. Small stages also cap what a mistake can cost.

At home

Change one thing, check it, then change the next. Don't upgrade the OS, Docker and Home Assistant in one evening.

CrowdStrike, 19 July 2024. A content update for the Falcon sensor went to every Windows host at once, with no staged rollout. About 8.5 million machines crashed into a boot loop. Airlines, hospitals and banks stopped work. The company's own review promised staged deployment with canary rings afterward.

Implementation: plan, read, then apply exactly that plan

tofu plan -out=stage1.tfplan
tofu show stage1.tfplan            # a human reads this
tofu apply stage1.tfplan           # applies only what was shown, nothing newer

scripts/destroy-guard.sh: fail the gate if the plan deletes anything not on an allowlist

#!/usr/bin/env bash
set -euo pipefail
plan=${1:?usage: destroy-guard.sh plan.tfplan}
allow=${2:-destroy_allowlist.txt}
deletes=$(tofu show -json "$plan" \
  | jq -r '.resource_changes[] | select(.change.actions | index("delete")) | .address')
bad=$(comm -23 <(sort -u <<<"$deletes" | sed '/^$/d') <(sort -u "$allow" 2>/dev/null || true))
if [[ -n "$bad" ]]; then
  echo "Refusing: plan deletes or replaces resources not on the allowlist:"; echo "$bad"; exit 1
fi
echo "OK: no unexpected deletes."

Before you design around a size or region, ask the API what this account can actually use: doctl compute size list and doctl compute region list. New accounts often don't get everything an old one had.

Check yourself. Add a resource rename to a test branch, so the plan wants to destroy and recreate it. The guard must exit 1 and name the resource.

7. Runbooks: how to run it, written before you need it

Each stage has an operator guide covering bootstrap, checks, what failure looks like, how to rotate every secret, and how to tear it down. Rotation only happens if its steps were written down on a calm day.

What it is for

Under stress, people skip steps and guess. A runbook turns a stressful job into reading and typing. It also lets someone else do it, which is how you get to take a holiday.

At home

Write down how to rebuild your most important box from nothing. Then test it on a spare SD card or a VM. The first test always finds a missing step.

Facebook, 4 October 2021. A maintenance command took the backbone offline. A bug in the audit tool failed to stop it. Engineers then could not reach the data centres remotely, and the badge systems depended on the same network, so recovery took about six hours. A recovery path that relies on the thing that is down is not a recovery path.

Implementation: one runbook step, in a format that works at 2am

runbooks/rebuild-pihole.md

## Rebuild Pi-hole from nothing          (last tested: 2026-11-02, took 25 min)

Needs: spare SD card, this repo, the restic password from the safe.

1. Run:     flash Raspberry Pi OS Lite; boot; ssh pi@raspberrypi.local
   Expect:  a shell prompt
   If not:  check the card in another reader; reflash
   Undo:    nothing to undo

2. Run:     git clone https://git.home/lab && cd lab/pihole && docker compose up -d
   Expect:  `docker compose ps` shows pihole "healthy" within 2 min
   If not:  `docker compose logs pihole | tail -50`; port 53 is often taken by systemd-resolved
   Undo:    docker compose down

3. Run:     restic restore latest --target / --include /srv/pihole
   Expect:  dig @127.0.0.1 ads.example.com returns 0.0.0.0
   If not:  restore went to the wrong path; check `restic ls latest | grep pihole`
   Undo:    rm -rf /srv/pihole; repeat step 3

4. Run:     point the router's DHCP DNS at the new Pi
   Expect:  a laptop on Wi-Fi gets the Pi as its DNS server
   Undo:    set router DNS back to 1.1.1.1

Keep the runbook in two places, and make sure one of them works when the lab is down: a printed copy, or a git clone on your laptop. A wiki hosted on the lab will be down when you need it.

Check yourself. Hand the runbook to someone else, or follow it yourself on a blank VM without looking anything up. Every time you have to improvise, add a line. Write the date of the test at the top.

8. Post-mortems without blame

After something breaks, write down the symptom, the real cause, the fix and the general lesson. Don't write down whose fault it was. The system let it happen. Fix the system.

What it is for

If people get punished for mistakes, they hide them, and the same gap breaks things again. If mistakes are safe to report, you learn about the gap the first time.

At home

After a 2am fix, write three lines in LESSONS.md before bed. Tomorrow you won't remember the error message that mattered.

AWS S3, 28 February 2017. An engineer ran a playbook command with a typo and removed far more servers than intended. S3 in us-east-1 went down for about four hours, and much of the internet with it. The public review did not blame the engineer. It changed the tool so it removes capacity slowly and refuses to go below a safe minimum. That fix protects every future operator.

Implementation

LESSONS.md: a real entry from the original wiki, rewritten in this format

## 2026-10-09: install "succeeded" but the connector never ran
Symptom:  `curl ... | bash` exited 0. The service was not running.
Cause:    The script read stdin, which was the pipe itself, and stopped early.
          The exit code came from the last command, not from the install.
Fix:      cloud-init writes the config itself, pins the apt key fingerprint,
          and only reports success if `systemctl is-active` says active.
Lesson:   Check the end state, not the exit code.

For a bigger incident, add a timeline, what went well, and action items with an owner and a due date each. An action item with no owner does not happen.

Check yourself. Read your last three lessons. Does any line name a person as the cause? Rewrite it as the missing guard: "nothing stopped a typo from removing 100 servers", not "Sam made a typo".

9. Verify, then write down that you verified

Every claim carries how and when it was checked: "masking was checked on the first real run", "backup pricing confirmed on 2026-10-11". A command that ran is not a thing that works.

What it is for

Unverified claims go stale without anyone noticing. A date tells the reader how much to trust a claim and when to check it again.

At home

Do the check that proves it works, not just that the command ran. For backups that means a restore. Write down the date.

GitLab.com, 31 January 2017. An engineer deleted the main production database by mistake while fighting a replication problem. GitLab had five backup and replication methods. None of them worked when needed: one had been failing silently because of a version mismatch, and its failure emails were being rejected. About six hours of data was lost. GitLab live-streamed the recovery and published a blameless review.

Implementation: prove the end state

scripts/verify-backup.sh: restore a random file and compare it to the original

#!/usr/bin/env bash
set -euo pipefail
repo=${RESTIC_REPOSITORY:?set RESTIC_REPOSITORY}
src=/srv/data
file=$(find "$src" -type f -size -50M | shuf -n1)
tmp=$(mktemp -d); trap 'rm -rf "$tmp"' EXIT
restic -r "$repo" restore latest --target "$tmp" --include "$file"
if cmp -s "$file" "$tmp$file"; then
  echo "$(date -I) restore OK: $file" | tee -a /var/log/backup-verified.log
else
  echo "RESTORE MISMATCH: $file" >&2; exit 1
fi
restic -r "$repo" check --read-data-subset=5%   # also read back 5% of the stored data

An install only counts if the service is really up

systemctl is-active --quiet myapp || { echo "myapp is not running"; exit 1; }
curl -fsS --max-time 5 http://127.0.0.1:8080/healthz >/dev/null || { echo "health check failed"; exit 1; }

Then alert on the absence of success, not only on errors. A job that silently stops running sends no error. With Prometheus and the node exporter's textfile collector, write a timestamp on each good run and alert when it gets old:

echo "backup_last_success_seconds $(date +%s)" > /var/lib/node_exporter/backup.prom
# alert rule:  time() - backup_last_success_seconds > 36 * 3600
Check yourself. When did you last restore a file from backup on purpose? If you can't give a date, you don't know your backups work.

10. Default to the boring, open, replaceable choice

Pick tools with open licenses, plain formats and a way out. The original project picks OpenTofu over Terraform for license reasons, DigitalOcean over AWS for a one-page price list, and Twingate while naming self-hosted options. Every vendor is a trust decision.

What it is for

Licenses change, prices rise, companies get bought, products get shut down. If leaving takes a weekend, those are annoyances. If it takes a rewrite, you are stuck.

At home

Before adopting a tool, ask what leaving it would take. Can you export the data in a standard format? Is the config in a file you own?

License changes, 2023–2024. HashiCorp moved Terraform and Vault to the Business Source License in August 2023; the community forked them as OpenTofu and OpenBao under the Linux Foundation. Redis changed its license in March 2024; the fork Valkey appeared within weeks. Teams on open formats switched in days. Teams that had built on closed features had to stay or rewrite.

Implementation: an exit check before you adopt anything

QuestionGood answerWarning sign
Where does my data live, and can I export it?Standard format (SQL dump, Markdown, OCI image, JSON)Export only through support, or as a vendor-only file
Is the config code I keep in git?Yes, a provider or a plain fileOnly clickable in a web console
Does it use open protocols?SSH, WireGuard, S3 API, OIDC, SMTPOwn client, own protocol

Write the answers in a short decision record next to the code:

docs/decisions/0004-ztna.md

# 0004: Use Twingate for remote access
Status:   accepted, 2026-10-01
Why:      outbound-only connectors (zero inbound ports); access as code via provider
Exit:     Headscale, NetBird or OpenZiti; resources are already defined in code,
          so moving means rewriting one module (~1 day, estimated)
Revisit:  if pricing changes or the free tier drops below 5 users
Check yourself. Pick your most-used lab service. Write the three commands to move it to a different host or vendor. If you can't, that is your biggest lock-in.

SOC 2 auditors look for the same thing in change management: they pick sample changes and ask you to show each one was requested, reviewed by someone other than the author, tested, approved and recorded. A merged PR with a green check and a review covers most of that by itself. A ticket written after the change is the classic finding.

Measuring it: the DORA metrics

The DORA research program tracks how often you deploy, how long a change takes to reach production, how often a change fails, and how fast you recover. In a homelab, the one worth tracking is change failure rate: changes that needed a fix or rollback, divided by all changes. Three bad changes out of twenty is 15%. If that number climbs, make your stages smaller.
