Cloud Security Review: Concepts, IAM, Compliance, IaC

Updated November 16, 2026

How to use this reviewer

Each of the four topics opens with a coarse view (the ideas you must be able to explain in two minutes) and then a deep dive (the mechanics, edge cases and examples an interviewer or exam will probe). Section 5 ties the four together with self-check questions and labs, and section 6 is a roadmap from beginner to principal-engineer and PhD level.

The four topics form one stack: concepts say what to protect and why, IAM controls who can touch it, compliance proves you did it, and IaC makes all of it repeatable and reviewable.

Examples lean on AWS, with Azure and GCP equivalents named. Framework versions are stated as of mid-2026 and written without a fresh lookup, so confirm dates on the official pages listed at the end before relying on them.

What's new in 2025–2026 (as of November 2026)

Five shifts matter most: AI agents became a new identity class to govern, post-quantum TLS went on by default at the big providers, AWS merged its detection tools into one Security Hub, FedRAMP moved to the 20x model, and Terraform/OpenTofu gained discovery and safety features. Each item links to its source.

Cloud security concepts: what changed

  • Unified cloud detection. At re:Invent 2025 AWS made the new Security Hub generally available; it correlates GuardDuty, Inspector, Security Hub CSPM and Macie findings into near-real-time risk analytics (AWS Security Blog). The old posture service is now called Security Hub CSPM. AWS also expanded GuardDuty Extended Threat Detection and previewed an AI AWS Security Agent (SiliconANGLE). Learn: threat vs exposure findings, multi-stage attack-sequence detection.
  • Post-quantum cryptography is in production. NIST finalized ML-KEM (FIPS 203), ML-DSA (FIPS 204) and SLH-DSA (FIPS 205) in August 2024. By April 2026 AWS had hybrid ML-KEM TLS on by default for KMS, ACM, Secrets Manager, Payment Cryptography and S3, and is removing the older Kyber support (AWS Builder Center). Google Cloud KMS made ML-KEM, ML-DSA and SLH-DSA keys GA and targets full PQC migration by 2029 (Google Cloud). Learn: harvest-now-decrypt-later, hybrid key exchange (X25519MLKEM768), crypto inventory and crypto agility.
  • AI agents are an attack surface. The OWASP Top 10 for Agentic Applications 2026 treats agents as operational actors with delegated authority and infrastructure access (CSA). Learn: prompt injection leading to tool misuse, excessive agency, data exfiltration through tools, poisoned models and plugins.
  • MCP (Model Context Protocol) security. Remote MCP servers are OAuth 2.1 resource servers. The 2026-07-28 spec requires the resource parameter (RFC 8707), HTTPS everywhere and PKCE, and clients must refuse servers whose authorization server lacks PKCE (MCP spec). Token passthrough (forwarding a client's token to a downstream API) is forbidden (MCP best practices). Real-world example: an SSRF in Azure MCP Server (CVE-2026-26118) let an attacker leak its managed-identity token (Gupta). Learn: tool poisoning, audience validation, least-privilege tool scopes.
  • CI/CD supply chain. 2025's compromised GitHub Action (tj-actions/changed-files) and self-spreading npm malware (Shai-Hulud) showed that pipelines holding cloud credentials are prime targets. Pin Actions to full commit SHAs and keep CI on short-lived OIDC credentials.

IAM: what changed

  • Non-human identities (NHIs) now dominate. Industry studies put NHIs at roughly 82 per human user (Wavestone). The CSA's July 2026 "Defining Non-Human Identity" report calls for separate governance: discovery, classification, an owner for every NHI, and short-lived tokens, workload identity federation and auto-renewed certificates instead of static secrets (Virtualization Review).
  • Dedicated identities for AI agents. Microsoft Entra Agent ID gives agents their own identities under Conditional Access, with specialized OAuth flows (Microsoft Learn); every agent identity must have at least one human sponsor (Entra docs changes). Third-party agents (e.g. on AWS Bedrock) can join through workload identity federation (Microsoft docs). AWS offers Bedrock AgentCore Identity for agent access to AWS and third-party tools (DEV). Learn: agent-on-behalf-of-user delegation, zero standing privilege, kill switches, per-action audit.
  • AWS IAM updates worth knowing:
  • IAM Policy Autopilot: open-source static-code analysis (launched re:Invent 2025) that generates IAM policies from your code (AWS); it became Terraform-aware in May 2026 (AWS).
  • Access-denied errors now name the ARN of the IAM or Organizations policy that denied you, within the same account and org (Jan 2026) (AWS).
  • Passkeys are supported as MFA for IAM and root users (SecurityWeek); combine with centralized root access management to remove root credentials from member accounts.
  • IAM Identity Center can now manage AWS application access without managing account access (Aug 2026) (AWS).
  • Quotas doubled for customer managed policies and instance profiles, to 10,000 per account (May 2026) (AWS).

1. Cloud security concepts

Coarse view

Cloud security is ordinary security (confidentiality, integrity, availability) applied to infrastructure you rent and drive through an API. Three facts change everything:

  • The control plane is the new perimeter. Anyone holding valid API credentials can create, read or delete infrastructure from anywhere. Identity, not the network edge, is the main boundary.
  • Responsibility is shared. The provider secures the cloud itself; you secure what you put in it and how you configure it.
  • Misconfiguration is the top cause of breaches. Public buckets, open security groups and over-privileged roles cause far more incidents than provider-side flaws.

Core principles to be able to define and apply:

Principle Meaning Cloud example
Least privilege Grant only the access a task needs, for only as long as it needs it Role scoped to one S3 prefix, not s3:*
Defense in depth Layer independent controls so one failure is not a breach SCP + IAM policy + bucket policy + encryption + logging
Zero trust Never trust by network location; verify identity, device and context on every request No flat VPN access; per-request auth via identity-aware proxy
Assume breach Design so a compromise is detected and contained Separate accounts per workload, alerting on unusual API calls
Blast radius Limit how much one failure or stolen credential can reach One account or project per environment and workload
Secure by default The safe setting is the default and deviations need approval S3 Block Public Access on at the org level
Immutability Replace rather than patch running resources Rebuild AMIs or container images, redeploy

Deep dive

Shared responsibility by service model

The more managed the service, the more the provider owns. Your data, identities and access configuration stay yours in every model.

Layer IaaS (EC2, VMs) PaaS (RDS, App Service, Cloud Run) SaaS (M365, Salesforce)
Data, classification, access policies Customer Customer Customer
Identities and accounts Customer Customer Customer
Application code Customer Customer Provider
Runtime, middleware Customer Provider Provider
Guest OS, patching Customer Provider Provider
Network config (security groups, firewall rules) Customer Shared Provider
Hypervisor, hardware, physical data centers Provider Provider Provider

Exam trap: encryption of data at rest is usually a customer configuration choice even when the provider supplies the mechanism.

Deployment models: public, private, hybrid, multi-cloud, community. Service models per NIST SP 800-145: IaaS, PaaS, SaaS. Essential characteristics: on-demand self-service, broad network access, resource pooling, rapid elasticity, measured service.

Organization structure and guardrails

The account, subscription or project is the strongest isolation boundary you control. Build a landing zone: a pre-secured multi-account layout created by code.

Concept AWS Azure GCP
Top container Organization Tenant + root management group Organization
Grouping Organizational Units (OUs) Management groups Folders
Isolation unit Account Subscription (+ resource groups) Project
Preventive guardrail Service Control Policies, Resource Control Policies Azure Policy (deny effect) Organization Policy constraints
Landing zone tooling Control Tower Azure Landing Zones (CAF) Cloud Foundation / Fabric FAST

Typical account layout: management (billing, org only, nothing else), security tooling, log archive (immutable), shared networking, and separate workload accounts per environment (dev, staging, prod).

Network security

  • VPC/VNet design: public subnets hold only load balancers and NAT; app and data tiers sit in private subnets with no public IPs.
  • Security groups (AWS) are stateful and allow-only, attached to network interfaces. NACLs are stateless, subnet-level, ordered allow and deny rules. Azure uses NSGs; GCP uses VPC firewall rules and hierarchical firewall policies.
  • Never allow 0.0.0.0/0 on SSH (22) or RDP (3389). Use AWS SSM Session Manager, Azure Bastion or GCP IAP TCP forwarding instead of bastion hosts with open ports.
  • Private access to services: VPC endpoints / PrivateLink, Azure Private Endpoints, GCP Private Service Connect keep traffic to storage and APIs off the internet.
  • Edge: WAF for layer-7 attacks (SQLi, XSS, bots), DDoS protection (AWS Shield, Azure DDoS Protection, Cloud Armor), CDN.
  • Egress control is often forgotten: restrict outbound traffic so stolen data and malware callbacks are blocked (egress firewall, DNS firewall).
  • Microsegmentation: in Kubernetes, NetworkPolicies default-deny pod-to-pod traffic.

Data protection and encryption

  • At rest: provider KMS (AWS KMS, Azure Key Vault, Cloud KMS). Know envelope encryption: a data encryption key (DEK) encrypts the data; a key encryption key (KEK) held in KMS encrypts the DEK. The KEK never leaves the KMS/HSM.
  • Key ownership options: provider-managed keys, customer-managed keys (CMK, you control policy and rotation), BYOK (you import key material), HYOK / external key store (key stays in your HSM). More control means more operational burden.
  • Key policy is access control: in AWS, a KMS key policy must allow use; denying kms:Decrypt makes the encrypted data unreadable even to admins with S3 access.
  • In transit: TLS 1.2+ everywhere, enforce with aws:SecureTransport conditions; mTLS for service-to-service.
  • Storage exposure: turn on S3 Block Public Access at org level; disable shared-key and anonymous access on Azure storage; use uniform bucket-level access on GCS.
  • Backups: immutable copies (S3 Object Lock, Azure immutable blobs, backup vault lock) in a separate account defend against ransomware and a compromised admin.
  • Data classification decides controls: public, internal, confidential, restricted. Tokenization and masking reduce how much sensitive data systems hold.

Secrets management

Secrets live in a secrets manager (AWS Secrets Manager, Azure Key Vault, GCP Secret Manager, HashiCorp Vault), are fetched at runtime by a workload identity, and rotate automatically. Never in source code, container images, plain environment files or Terraform state. Prefer no secret at all: IAM database auth, workload identity federation, short-lived tokens.

Logging, monitoring and detection

Signal AWS Azure GCP
Control-plane audit log CloudTrail (management events; data events cost extra) Activity Log + Entra sign-in/audit logs Cloud Audit Logs (Admin Activity always on; Data Access opt-in)
Network flow VPC Flow Logs NSG / VNet flow logs VPC Flow Logs
Threat detection GuardDuty Defender for Cloud Security Command Center
Findings hub / posture Security Hub (unified, GA Dec 2025), Security Hub CSPM, Config Defender for Cloud, Azure Policy Security Command Center
SIEM Security Lake + any SIEM Microsoft Sentinel Google SecOps

Centralize logs into the log-archive account, make them immutable, and alert on high-signal events: root login, CloudTrail stopped, IAM policy changes, security group opened to the world, access key created for a user, unusual region activity.

Tool categories (acronyms you will see)

  • CSPM (posture management): finds misconfigurations against benchmarks like CIS.
  • CWPP (workload protection): vulnerabilities and runtime threats on VMs, containers, serverless.
  • CIEM (entitlement management): finds excessive and unused permissions.
  • DSPM (data posture): finds where sensitive data lives and who can reach it.
  • CNAPP: a platform combining the above plus IaC scanning.

Workload security

  • VMs: hardened golden images, patching via SSM/Update Manager, IMDSv2 required (session-token metadata service; blocks the SSRF-to-credentials attack used in the 2019 Capital One breach).
  • Containers: minimal base images, image scanning in CI and registry, signed images, non-root user, read-only root filesystem, no privileged pods, resource limits.
  • Kubernetes: RBAC with no cluster-admin for apps, Pod Security Standards (restricted), admission control (Kyverno, OPA Gatekeeper), NetworkPolicies, private API endpoint, secrets encrypted with KMS.
  • Serverless: one role per function, scoped triggers, dependency scanning; the attack surface shifts to code and permissions.

Common cloud attack paths

  1. Leaked access key (public GitHub repo, CI logs) used to enumerate and pivot.
  2. SSRF in a web app reaches the instance metadata service and steals role credentials.
  3. Over-privileged role allows privilege escalation (for example iam:PassRole plus lambda:CreateFunction).
  4. Public storage bucket or snapshot exposes data.
  5. Compromised account used for cryptomining in unused regions.
  6. Supply chain: malicious package, base image or Terraform module.

Incident response in the cloud

Follow NIST SP 800-61 (Rev. 3 aligns IR with CSF 2.0). Cloud-specific moves: isolate an instance by swapping in a quarantine security group, snapshot disks and memory for forensics before terminating, revoke active role sessions (AWS aws:TokenIssueTime deny), disable and rotate keys, and query CloudTrail for everything the stolen principal did. Pre-build IR roles and runbooks; you cannot request access during an incident.

Resilience

Availability is part of security. Know RTO (how long you can be down) and RPO (how much data you can lose). Spread across availability zones by default and across regions when the RTO demands it. Test restores, not just backups.

2. Identity and access management (IAM)

Coarse view

IAM answers two questions on every request: who are you (authentication, AuthN) and what may you do (authorization, AuthZ). In the cloud, every API call is an IAM decision, so IAM is the real perimeter.

  • Principals are humans (employees, admins) and workloads (VMs, functions, pods, CI pipelines). Workload identities now outnumber humans many times over.
  • Credentials should be short-lived. Humans sign in through SSO with MFA and get temporary sessions; workloads use roles or federated tokens. Long-lived access keys and service-account keys are the most common leaked secret.
  • Least privilege is a process, not a setting. Start narrow, use access analysis to trim unused permissions, review access regularly.
  • Identity lifecycle (joiner–mover–leaver): provision on hire, adjust on role change, revoke on exit. Movers who keep old access cause privilege creep.

Deep dive

Authentication

  • MFA strength: SMS < TOTP app < push with number matching < phishing-resistant FIDO2/WebAuthn (security keys, passkeys). Require phishing-resistant MFA for admins.
  • SAML 2.0: XML assertions from an identity provider (IdP) to a service provider (SP); common for enterprise SSO into cloud consoles.
  • OAuth 2.0 is delegated authorization (an access token lets an app act on your behalf). OpenID Connect (OIDC) adds authentication on top with a signed ID token (JWT). Use Authorization Code + PKCE for apps; avoid the implicit flow.
  • SCIM automates user and group provisioning from the IdP to apps, which makes leaver revocation reliable.
  • Conditional / context-aware access: decisions consider device health, location, risk score (Entra Conditional Access, Google Context-Aware Access, Okta policies).

Access control models

Model Decision based on Strength Weakness
DAC Owner grants access Flexible Inconsistent, hard to audit
MAC Labels and clearances set by policy Strong, central Rigid
RBAC Roles grouping permissions Easy to audit Role explosion
ABAC Attributes (tags) of principal, resource, environment Scales with few policies Harder to reason about; tag hygiene critical
ReBAC Relationships (user is editor of doc in folder) Fits app-level sharing (Google Zanzibar, OpenFGA) Needs a dedicated authZ service

Cloud IAM is RBAC at its core with ABAC conditions layered on (AWS tags in conditions, Azure ABAC conditions, GCP IAM Conditions).

AWS IAM in depth

Principals: root user (lock away, MFA, no access keys), IAM users (avoid for humans), IAM roles (assumed via STS for temporary credentials), federated identities via IAM Identity Center (formerly AWS SSO).

Policy types, from broadest guardrail to narrowest:

Policy type Attached to Grants? Purpose
Service Control Policy (SCP) Org, OU, account No, only limits Max permissions for principals in member accounts
Resource Control Policy (RCP) Org, OU, account No, only limits Max permissions on resources, e.g. block access from outside the org
Permissions boundary User or role No, only limits Lets developers create roles without escalating
Identity-based policy User, group, role Yes What this principal may do
Resource-based policy S3 bucket, KMS key, SQS, Lambda… Yes Who may use this resource; enables cross-account
Session policy Passed at AssumeRole No, only limits Narrows one session

Evaluation rules to memorize (the flow diagram below shows the order):

  1. Everything starts as an implicit deny.
  2. An explicit deny anywhere wins, always.
  3. SCPs, RCPs, permissions boundaries and session policies must all allow (they are filters, not grants).
  4. Same account: an allow in the identity policy or the resource policy is enough.
  5. Cross-account: the identity policy in the caller's account and the resource policy (or role trust policy) in the target account must both allow.

Read it top down: any explicit deny ends the request, the org guardrails must allow, and a same-account resource-policy allow can skip the identity check.

Policy anatomy (Effect, Action, Resource, Condition, plus Principal in resource policies):

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadReportsPrefixOnly",
      "Effect": "Allow",
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::acme-data/reports/*",
      "Condition": {
        "Bool": {"aws:SecureTransport": "true"},
        "StringEquals": {"aws:PrincipalOrgID": "o-abc123"}
      }
    }
  ]
}

Useful global condition keys: aws:PrincipalOrgID, aws:SourceVpce, aws:SourceIp, aws:MultiFactorAuthPresent, aws:SecureTransport, aws:PrincipalTag/*, aws:ResourceTag/*, aws:RequestedRegion.

Roles and trust: a role has a trust policy (who may assume it) and permission policies (what it can do). For third parties use an external ID in the trust policy to prevent the confused deputy problem. Never trust "Principal": "*" without tight conditions.

Privilege escalation paths to recognize:

  • iam:PassRole + ec2:RunInstances or lambda:CreateFunction: launch compute with a more powerful role.
  • iam:CreatePolicyVersion / iam:SetDefaultPolicyVersion: rewrite your own policy.
  • iam:AttachUserPolicy, iam:PutRolePolicy: grant yourself admin.
  • iam:UpdateAssumeRolePolicy: add yourself to a powerful role's trust.
  • iam:CreateAccessKey on another user.

Scope iam:PassRole with a Resource list of specific role ARNs and an iam:PassedToService condition.

Tooling: IAM Access Analyzer (external access findings, unused access, policy validation and generation from CloudTrail), credential report, last-accessed data, IAM policy simulator.

Azure IAM

  • Microsoft Entra ID (formerly Azure AD) is the identity provider: users, groups, app registrations, service principals.
  • Two separate role systems, a classic exam trap: Entra roles govern the directory (Global Administrator, User Administrator); Azure RBAC roles govern resources (Owner, Contributor, Reader, plus granular built-ins).
  • Azure RBAC assignment = security principal + role definition + scope. Scopes inherit downward: management group → subscription → resource group → resource. Deny assignments exist but are mostly system-created.
  • Managed identities (system-assigned, tied to one resource; user-assigned, reusable) remove the need for secrets.
  • Privileged Identity Management (PIM): just-in-time, time-boxed, approval-gated role activation.
  • Conditional Access: policies on sign-in (require MFA, compliant device, block legacy auth).
  • Azure Policy is governance (what may be deployed), not access control.

GCP IAM

  • An allow policy binds principals to roles on a resource. Policies inherit down the hierarchy: organization → folders → project → resource. Effective access is the union of all inherited bindings, so a grant at the org level cannot be removed lower down.
  • Role types: basic (Owner, Editor, Viewer; too broad, avoid in prod), predefined (per service), custom.
  • IAM deny policies override allows; IAM Conditions add attribute rules (time, resource name, tags).
  • Service accounts are workload identities. Avoid downloadable service-account keys; disable key creation with the org policy constraint iam.disableServiceAccountKeyCreation. Watch iam.serviceAccountUser and iam.serviceAccountTokenCreator: they allow impersonation.
  • Workload Identity Federation lets AWS, Azure, GitHub Actions or on-prem OIDC/SAML identities get GCP tokens without keys.

Workload identity (no static secrets)

Workload AWS Azure GCP
VM Instance profile (role) Managed identity Attached service account
Kubernetes pod EKS Pod Identity / IRSA Entra Workload ID GKE Workload Identity Federation
CI/CD (e.g. GitHub Actions) OIDC provider + AssumeRoleWithWebIdentity Federated credential on app registration Workload Identity Federation

For CI, the trust condition must pin the repository and branch or environment (the token's sub claim), otherwise any repo on the platform could assume your role. SPIFFE/SPIRE provides the same idea for service-to-service identity across platforms.

Privileged access management

  • Just-in-time (JIT) elevation instead of standing admin access.
  • Break-glass accounts: two emergency accounts, excluded from SSO dependency, hardware MFA, monitored with alerts on any use.
  • Separation of duties (SoD): the person who writes a change is not the one who approves or deploys it.
  • Session recording and approval workflows for production access.

Governance

Periodic access reviews (recertification), removal of unused roles and permissions, tagging owners on every role, and alerting on new admin grants. Metrics worth tracking: number of principals with admin, number of long-lived keys, percentage of unused permissions.

Common IAM mistakes

  • "Action": "*" and "Resource": "*" in app roles.
  • Access keys for humans or CI instead of SSO and OIDC federation.
  • Daily use of the root account or Global Administrator.
  • One shared role for every Lambda or every pod.
  • Trust policies open to a whole account or to * without conditions.
  • Forgetting that resource policies (S3, KMS, SQS) can grant access the identity side never shows.

3. Compliance frameworks

Coarse view

Compliance is proving to an outside party that your security controls exist and work. Security is the practice; compliance is the evidence. You can be compliant and still insecure, so treat frameworks as a floor.

Know the four kinds of documents and do not mix them up:

  • Laws and regulations are mandatory where they apply (GDPR, HIPAA, the Philippine Data Privacy Act).
  • Standards are published requirement sets, often certifiable (ISO/IEC 27001, PCI DSS).
  • Frameworks are voluntary structures for organizing a program (NIST CSF, CIS Controls).
  • Attestations and certifications are the auditor's output (a SOC 2 report, an ISO certificate, a FedRAMP authorization).

In the cloud, compliance is shared just like security. You inherit the provider's physical and infrastructure controls (download their reports from AWS Artifact, Microsoft Service Trust Portal, Google Cloud Compliance Reports Manager), but you still own everything you configure.

ISO/IEC 27001:2022

  • Certifies an Information Security Management System (ISMS): a risk-driven management process, not just a list of controls.
  • Clauses 4–10 are mandatory: context, leadership, planning (risk assessment and treatment), support, operation, performance evaluation (internal audit, management review), improvement.
  • Annex A has 93 controls in four themes: Organizational (37), People (8), Physical (14), Technological (34). New in 2022 and cloud-relevant: 5.7 threat intelligence, 5.23 information security for use of cloud services, 8.9 configuration management, 8.12 data leakage prevention, 8.16 monitoring activities, 8.28 secure coding.
  • Key artifact: the Statement of Applicability (SoA) listing every Annex A control, whether it applies and why.
  • Cycle: stage 1 audit (documentation) → stage 2 audit (implementation) → certificate valid 3 years with annual surveillance audits.
  • Cloud extensions: ISO/IEC 27017 (cloud security controls), 27018 (PII protection in public cloud), 27701 (privacy management).

SOC 2

  • An auditor's (CPA firm) report, not a certificate. Customers read it under NDA.
  • Trust Services Criteria: Security (the Common Criteria, always required), plus optional Availability, Processing Integrity, Confidentiality, Privacy.
  • Type I: controls are suitably designed at a point in time. Type II: controls operated effectively over a period (commonly 6–12 months). Customers usually want Type II.
  • Know CUECs (complementary user entity controls: what the customer must do for the vendor's controls to work) and subservice organizations (e.g. AWS) reported with the carve-out or inclusive method.
  • SOC 1 covers controls relevant to customers' financial reporting; SOC 3 is a public, short version of SOC 2.

NIST CSF 2.0 and SP 800-53

  • CSF 2.0 added Govern as a sixth function wrapping the other five. Use it with Profiles (current vs target) and Tiers (Partial, Risk Informed, Repeatable, Adaptive).
  • 800-53 Rev. 5 is the detailed control catalog behind FedRAMP and US federal systems. Families you meet constantly in cloud work: AC (access control), AU (audit and accountability), CM (configuration management), IA (identification and authentication), SC (system and communications protection), SI (system and information integrity), IR (incident response), CP (contingency planning), RA (risk assessment), SR (supply chain).
  • The NIST Risk Management Framework (SP 800-37): Prepare, Categorize, Select, Implement, Assess, Authorize, Monitor.

PCI DSS 4.0.1

  • 12 requirements, e.g. Req. 1 network security controls, Req. 3 protect stored account data, Req. 7–8 access and authentication (MFA for all access into the cardholder data environment), Req. 10 logging, Req. 11 testing, Req. 12 policies.
  • Scope is everything. Shrink the cardholder data environment (CDE) with network segmentation, tokenization or a hosted payment page so fewer systems are in scope.
  • 4.0 introduced the customized approach (meet the objective your own way, with more evidence) alongside the defined approach.
  • Levels by transaction volume decide whether you need a QSA-led Report on Compliance or a Self-Assessment Questionnaire.

Privacy laws (GDPR and the Philippine DPA)

  • Roles: controller decides why and how data is processed; processor acts on its instructions (a cloud provider is usually a processor). Contracts: GDPR Art. 28 data processing agreement; the PH DPA uses data sharing and outsourcing agreements.
  • Security obligation: "appropriate technical and organizational measures" (GDPR Art. 32; NPC Circular 16-01 for the PH, which also requires a Data Protection Officer and registration for larger processors).
  • Breach notification within 72 hours of knowledge to the regulator in both regimes.
  • Cloud angle: data residency and cross-border transfers (EU Standard Contractual Clauses, EU–US Data Privacy Framework), encryption, access logging, deletion on request.

Other names you should recognize

  • NIS2 (EU, essential and important entities) and DORA (EU financial sector, applies since Jan 2025, heavy on ICT third-party and cloud risk).
  • ISO/IEC 42001 for AI management systems, increasingly paired with 27001.
  • CMMC for US defense contractors, based on NIST SP 800-171.

How compliance actually runs

  1. Scope: which systems, data, accounts and teams are in scope. Good account structure makes this easy.
  2. Gap assessment against the framework.
  3. Common control framework: map one internal control to many frameworks (an MFA control satisfies ISO 5.17/8.5, SOC 2 CC6.1, PCI Req. 8, 800-53 IA-2). Build once, prove many times.
  4. Implement controls, preferably as code and preventive guardrails.
  5. Collect evidence continuously: config snapshots, logs, tickets, access reviews, training records.
  6. Audit: the auditor tests design (does the control address the risk?) and operating effectiveness (did it work every time across a sample?). Failures become exceptions; gaps go to a risk register or a POA&M (plan of action and milestones).
  7. Monitor and repeat.

Continuous compliance in the cloud: AWS Config conformance packs and Security Hub standards (CIS, PCI, NIST 800-53), AWS Audit Manager; Azure Policy regulatory compliance initiatives and Defender for Cloud; GCP Security Command Center compliance and Assured Workloads. Platforms such as Vanta, Drata and Secureframe automate evidence collection for SOC 2 and ISO.

Audit vocabulary: control objective, control activity, test of design, test of operating effectiveness, sampling, exception, compensating control, management assertion, qualified opinion, risk acceptance.

4. Infrastructure as code (IaC)

Coarse view

IaC defines infrastructure in version-controlled files and lets a tool create and change it. For security this matters because every change becomes reviewable (pull requests), testable (scanners and policy checks before deploy), repeatable (the same secure baseline in every account) and auditable (git history is evidence).

Key terms:

  • Declarative (describe the end state: Terraform, CloudFormation, Bicep) vs imperative (describe the steps: scripts, some Pulumi and Ansible usage).
  • Idempotent: applying the same config twice gives the same result.
  • Desired state vs actual state; the difference is drift.
  • Immutable infrastructure: replace resources instead of modifying them in place.
  • Shift left: catch misconfigurations at code-review time, where they are cheapest to fix.

Deep dive

Terraform/OpenTofu mechanics

  • Building blocks: providers (API plugins), resources (things to manage), data sources (read-only lookups), variables, locals, outputs, modules (reusable packages).
  • Workflow: init (download providers and modules) → plan (diff desired vs actual) → apply → destroy. Always review the plan; it is the change request.
  • Use for_each over count for collections so removing one item does not shift addresses and destroy others.
  • Refactoring without destroy: moved blocks, import blocks (bring existing resources under management), removed blocks.

State: the most sensitive file you own

  • State maps code to real resource IDs and stores attribute values in plaintext, including secrets (database passwords, private keys). sensitive = true only hides values from CLI output; they are still in state.
  • Store state in a remote backend (S3, Azure Blob, GCS, HCP Terraform) with encryption, versioning, locking and tight IAM. Recent Terraform versions lock natively in S3 (use_lockfile = true), replacing the old DynamoDB lock table.
  • Never commit state or .tfvars with secrets to git.
  • Keep secrets out of state where possible: reference a secrets manager ARN instead of the value, let the service generate and manage the password (e.g. RDS manage_master_user_password), and use ephemeral values and write-only arguments in recent Terraform releases. OpenTofu can encrypt state client-side.
  • Split state by environment and component (network, IAM, data, app). Smaller state means a smaller blast radius and faster plans. Prefer separate directories or stacks per environment over CLI workspaces for prod isolation.

Secure-by-default module example

resource "aws_s3_bucket" "logs" {
  bucket = "acme-prod-logs"
}

resource "aws_s3_bucket_public_access_block" "logs" {
  bucket                  = aws_s3_bucket.logs.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_s3_bucket_server_side_encryption_configuration" "logs" {
  bucket = aws_s3_bucket.logs.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm     = "aws:kms"
      kms_master_key_id = aws_kms_key.logs.arn
    }
  }
}

resource "aws_s3_bucket_versioning" "logs" {
  bucket = aws_s3_bucket.logs.id
  versioning_configuration { status = "Enabled" }
}

Package patterns like this as an internal module so teams get encryption, versioning and public-access blocking without remembering them. Pin versions: required_version, required_providers with constraints, commit .terraform.lock.hcl, and reference modules by tag or commit SHA.

package terraform.sg

deny contains msg if {

A secure IaC pipeline

  1. Developer opens a pull request; branch protection requires review and passing checks.
  2. CI runs fmt, validate, TFLint, secret scan and IaC scan.
  3. CI runs plan with a read-only role, posts the plan to the PR, and runs policy-as-code against plan JSON.
  4. A second person reviews code and plan (separation of duties).
  5. On merge, CI runs apply with a separate apply role, using the saved plan, gated by an environment approval for prod.
  6. CI authenticates by OIDC federation, never stored cloud keys. The role trust policy pins repo and branch or environment.
  7. Scheduled drift detection (plan -refresh-only or plan -detailed-exitcode) alerts when reality differs from code.

Orchestration options: GitHub Actions or GitLab CI, Atlantis, HCP Terraform, Spacelift, env0. For Kubernetes, GitOps (Argo CD, Flux) pulls desired state from git and reconciles continuously, so the cluster needs no inbound CI credentials.

  id-token: write

Drift and break-glass changes

Console changes ("ClickOps") break the guarantee that code equals reality. Deny write access in prod to humans except through break-glass roles; when an emergency change happens, back-port it into code and re-apply. Treat unexplained drift as a possible security event.

IaC supply chain

Third-party modules and providers run with your cloud credentials. Pin to exact versions or commit SHAs, review module source, mirror approved modules in a private registry, verify provider checksums through the lock file, and sign commits. SLSA levels describe how much build provenance you can prove.

IaC anti-patterns

  • Hardcoded secrets in .tf files or default variable values.
  • One giant state for everything.
  • apply -auto-approve to prod from a laptop.
  • Admin-level CI credentials shared by every pipeline.
  • Modules that default to insecure settings and rely on callers to fix them.
  • Ignoring scanner findings with blanket skips instead of documented, per-resource exceptions.

5. Putting it together, self-check and labs

How the four topics connect

One requirement traced through all four layers shows the pattern. Take "customer data must be encrypted and only reachable by the billing service":

  1. Concept: data protection with least privilege and defense in depth.
  2. IAM: a dedicated role for the billing service, a KMS key policy allowing only that role to decrypt, a bucket policy restricted to the org and a VPC endpoint.
  3. IaC: all of the above written as a module, scanned in CI, applied through a reviewed pipeline; an SCP blocks disabling encryption.
  4. Compliance: the same control maps to ISO 27001 8.24, SOC 2 CC6.1/CC6.7, PCI DSS Req. 3, and NIST SC-28; evidence is the PR history, the scan results and the Config rule showing continuous compliance.

Self-check questions

Answer out loud before reading the hint.

  1. A bucket policy allows a role in another account, but the role's identity policy is silent. Is access allowed? No: cross-account needs both sides to allow.
  2. An SCP allows only s3:*. A user has AdministratorAccess. Can they launch EC2? No: SCPs cap the maximum.
  3. Why is IMDSv2 a security control? It requires a session token from a PUT request, which blocks most SSRF-based credential theft.
  4. Difference between OAuth 2.0 and OIDC? OAuth delegates authorization; OIDC adds an ID token for authentication.
  5. What does an external ID prevent? The confused deputy problem in third-party role assumption.
  6. Azure: a user is Global Administrator. Can they delete a VM? Not by default: Entra roles and Azure RBAC are separate (though a Global Admin can elevate to User Access Administrator).
  7. GCP: Editor granted at the folder, you remove it at the project. Effect? None: allow policies are a union; use a deny policy or remove the folder grant.
  8. SOC 2 Type I vs Type II? Design at a point in time vs operating effectiveness over a period.
  9. Name the six NIST CSF 2.0 functions. Govern, Identify, Protect, Detect, Respond, Recover.
  10. What is a Statement of Applicability? The ISO 27001 list of Annex A controls, applicability and justification.
  11. How do you reduce PCI DSS scope? Segmentation, tokenization, outsourced payment pages.
  12. Where do Terraform secrets leak even when marked sensitive? The state file.
  13. Why scan the plan JSON and not only the HCL? Variables, modules and computed values are resolved there.
  14. Why separate plan and apply roles in CI? A compromised PR can run plan; it must not be able to change infrastructure.
  15. Envelope encryption in one sentence? Data is encrypted with a data key, and the data key is encrypted with a master key that never leaves KMS.

Hands-on labs

  • Play flaws.cloud and flaws2.cloud (free AWS misconfiguration challenges, attacker and defender paths).
  • Run CloudGoat scenarios in a sandbox account to practise IAM privilege escalation.
  • Scan a sandbox account with Prowler or ScoutSuite and fix the top findings against the CIS AWS Foundations Benchmark.
  • Build a small landing zone in Terraform or OpenTofu: org, two OUs, an SCP that denies leaving the org and disabling CloudTrail, a log-archive account.
  • Set up GitHub Actions to Terraform with OIDC, separate plan and apply roles, Checkov or Trivy, and a Conftest policy.
  • Use LocalStack for cheap local IaC experiments; tear real resources down with destroy to avoid bills.
  • Map ten controls you built to ISO 27001 Annex A and SOC 2 criteria in a spreadsheet: this is exactly what auditors ask for.

6. Roadmap: beginner to principal and PhD level

Sections 1–5 cover what a strong practitioner must know. Getting to principal-engineer or PhD level needs three more things: deeper foundations under the cloud abstractions, adjacent specialties the current reviewer only touches, and skills that are not technical knowledge at all (judgment, research, influence).

Be realistic about time. Study can make you an expert in about 3–5 years of steady part-time work. Principal-level judgment also needs years of owning real systems and incidents, and a PhD-level contribution means producing new knowledge, not just absorbing it. The ladder below shows what to prove at each step.

New modules

Each module lists what to learn, in rough order, and one exercise that proves it.

Module A: Foundations under the cloud (L0–L2)

  • Networking: OSI vs TCP/IP layers, subnetting and CIDR math, routing, NAT, TCP handshake and state, DNS resolution and DNSSEC, HTTP/1.1 vs 2 vs 3 (QUIC), TLS 1.3 handshake, certificates and PKI, mTLS.
  • Linux and OS internals: processes, users, capabilities, file permissions, SELinux/AppArmor, namespaces and cgroups (what a container really is), seccomp, eBPF basics, the boot chain.
  • Applied cryptography: symmetric (AES-GCM) vs asymmetric (RSA, ECDSA, Ed25519), hashes vs MACs vs signatures, key derivation (HKDF, Argon2), nonces and why reuse is fatal, envelope encryption, PKI and certificate transparency, post-quantum algorithms (ML-KEM, ML-DSA). Rule: never write your own crypto; learn to spot misuse.
  • Distributed systems: CAP and consistency models, eventual consistency (IAM changes propagate with delay), clocks and ordering, consensus (Raft), idempotency and retries, failure modes.
  • Exercise: capture a TLS 1.3 handshake in Wireshark and annotate every message; build a container by hand with unshare and cgroups.

Module B: Threat modeling and security architecture (L2–L4)

  • Threat modeling methods: the Four Question Framework (What are we working on? What can go wrong? What are we going to do about it? Did we do a good job?), STRIDE, attack trees, PASTA, LINDDUN for privacy, MITRE ATT&CK Cloud Matrix for real adversary techniques.
  • Design principles (Saltzer and Schroeder): least privilege, fail-safe defaults, complete mediation, economy of mechanism, separation of privilege, least common mechanism, psychological acceptability.
  • Architecture patterns: zero trust (NIST SP 800-207), identity-aware proxies, cell-based architecture for blast-radius control, data perimeters, paved roads and secure defaults.
  • Security design review: reading a design doc, finding the trust boundaries, writing actionable findings ranked by risk.
  • Exercise: threat-model one of your own apps with a data-flow diagram, STRIDE per element, and a ranked mitigation list.

Module C: Kubernetes and software supply chain (L2–L3)

  • Kubernetes security: API server authN/authZ, RBAC design, service accounts and projected tokens, Pod Security Standards, admission control (Kyverno, Gatekeeper, ValidatingAdmissionPolicy), NetworkPolicies, secrets and KMS encryption, node hardening, runtime detection (Falco, Tetragon), multi-tenancy limits.
  • Supply chain: SBOMs (SPDX, CycloneDX), signing and verification (Sigstore: cosign, Fulcio, Rekor), provenance and SLSA levels, in-toto attestations, dependency pinning and update bots, reproducible builds, securing CI runners.
  • Exercise: build a pipeline that produces a signed image with an SBOM and SLSA provenance, and an admission policy that rejects unsigned images.

Module D: Detection engineering and incident response (L2–L3)

  • Log sources and their gaps (CloudTrail data events, Kubernetes audit logs, flow logs, identity provider logs).
  • Detection as code: Sigma rules, testing detections against simulated attacks, tuning false positives, mapping coverage to ATT&CK.
  • Incident response: NIST SP 800-61 Rev. 3, incident command roles, cloud forensics (snapshots, memory capture, timeline building), blameless postmortems.
  • Exercise: run Stratus Red Team techniques in a sandbox and write detections that catch each one.

Module E: Offensive cloud security (L2–L3)

  • Cloud attack lifecycle: initial access (leaked keys, SSRF, exposed services), enumeration, privilege escalation, lateral movement across accounts, persistence, exfiltration.
  • Tools: Pacu, CloudGoat, Stratus Red Team, ScoutSuite, Prowler; Kubernetes Goat; IAM privilege-escalation path tools (for example PMapper).
  • Ethics: only test what you own or are authorized in writing to test; follow provider penetration-testing policies.
  • Exercise: complete every CloudGoat scenario, then write the defensive control that would have stopped each.

Module F: AI and agent security (L3)

  • Threats: direct and indirect prompt injection, data and model poisoning, model extraction, sensitive data leakage, excessive agency, insecure tool use.
  • Frameworks: OWASP Top 10 for LLM Applications and for Agentic Applications, MITRE ATLAS, NIST AI RMF, CSA AI Controls Matrix, ISO/IEC 42001.
  • Engineering controls: agent identity and scoped delegation, MCP with OAuth 2.1, tool allow-lists, human approval for high-impact actions, output validation, sandboxed code execution, evaluation and red-teaming of models.
  • Exercise: build an MCP server in Go with proper OAuth 2.1 audience validation, then red-team it with indirect prompt injection.

Module G: Confidential computing and data-in-use protection (L3)

  • Trusted execution environments: AWS Nitro Enclaves, AMD SEV-SNP, Intel TDX, confidential VMs and GPUs on all three clouds.
  • Remote attestation: proving what code runs before releasing a key (KMS policies keyed on enclave measurements).
  • Limits: side channels (Spectre-class attacks), trust in the hardware vendor.
  • Exercise: run a Nitro Enclave that only receives a KMS decryption key after attestation succeeds.

Module H: Formal methods and automated reasoning (L4–L5)

  • Why: at cloud scale, testing a few cases is not enough; providers use mathematical proof to answer "can anyone outside my org ever read this bucket?"
  • Learn: propositional logic, SAT/SMT solvers (Z3), how AWS Zelkova turns IAM policies into SMT formulas (the engine behind IAM Access Analyzer), verifiable policy languages (Cedar), model checking with TLA+ for distributed protocols.
  • Exercise: encode a small subset of IAM policy evaluation in Z3 (Go or Python bindings) and prove or refute "no public read" for sample policies.

Module I: Principal-engineer skills (L4)

  • Risk and prioritization: quantitative risk (FAIR model, ranges instead of red/amber/green), risk registers, deciding what not to fix.
  • Strategy: multi-year security roadmaps, build vs buy, platform thinking (secure paved roads that teams choose because they are easier).
  • Writing: design docs, RFCs, one-page decision memos, postmortems. Principal impact travels through documents.
  • Influence: aligning teams without authority, mentoring, saying no with an alternative, presenting risk to executives in business terms.
  • Metrics: measure outcomes (mean time to remediate, % of workloads without long-lived credentials, detection coverage) rather than activity.
  • Exercise: write a 2-page strategy memo proposing an org-wide change (for example "eliminate long-lived cloud keys in 12 months") with costs, risks and milestones.

Research track (toward PhD level)

Landmark papers to read, in this order:

  1. Saltzer and Schroeder, The Protection of Information in Computer Systems (1975): the design principles still used today.
  2. Thompson, Reflections on Trusting Trust (1984): the original supply-chain attack argument.
  3. Ristenpart et al., Hey, You, Get Off of My Cloud (ACM CCS 2009): co-residency attacks in public clouds.
  4. Ward and Beyer, BeyondCorp: A New Approach to Enterprise Security (;login:, 2014): the zero-trust blueprint.
  5. Backes et al., Semantic-based Automated Reasoning for AWS Access Policies using SMT (FMCAD 2018): Zelkova, the math behind IAM Access Analyzer.
  6. Kocher et al., Spectre Attacks: Exploiting Speculative Execution (IEEE S&P 2019): why hardware isolation leaks.
  7. Pang et al., Zanzibar: Google's Consistent, Global Authorization System (USENIX ATC 2019): relationship-based authorization at planet scale.
  8. Torres-Arias et al., in-toto: Providing farm-to-table guarantees for bits and bytes (USENIX Security 2019): supply-chain integrity.
  9. Greshake et al., Not what you've signed up for: Compromising Real-World LLM-Integrated Applications with Indirect Prompt Injection (2023): the founding paper of agent security.
  10. Cutler et al., Cedar: A New Language for Expressive, Fast, Safe, and Analyzable Authorization (OOPSLA 2024): verified policy language design.

How to read papers: use S. Keshav's three-pass method (skim structure; read for argument; re-derive the details). Keep a one-paragraph summary per paper: problem, method, result, limitation, idea it gives you.

Venues to follow: the top four academic security conferences (USENIX Security, IEEE S&P, ACM CCS, NDSS), plus practitioner venues fwd:cloudsec, AWS re:Inforce and KubeCon's security events. Read the accepted-paper lists each year and pick the cloud, identity and supply-chain papers.

From reader to researcher:

  1. Reproduce a published result (for example, re-run an IAM privilege-escalation analysis on your own test accounts).
  2. Extend it: new cloud, new policy type, larger scale, or a counter-measure.
  3. Evaluate honestly: define a dataset, metrics and a baseline before you build.
  4. Write it up: a detailed blog post first, then a workshop paper, then a conference submission.
  5. Find collaborators: a university security lab, or a mentor through open-source projects in this space (OPA, Cedar, OpenTofu, Prowler, Sigstore).

If you want the formal credential, a master's or PhD in security is the structured path; the steps above are how you test whether you enjoy research first.

Open problems worth exploring: least-privilege policy synthesis from real usage, authorization for AI agents acting on behalf of users, verifying IaC changes before deploy, post-quantum migration at scale, and detecting abuse of non-human identities.

Study system

  • Cadence: a steady 5–7 hours a week beats occasional long sessions. Suggested split: 50% building, 30% reading, 20% review and writing.
  • Retention: put definitions, evaluation rules and framework structures into spaced-repetition flashcards (Anki or similar) on the day you learn them; review daily for 10 minutes.
  • Explain to learn: after each module, write a one-page explanation as if teaching a junior engineer. Gaps in the explanation are gaps in understanding.
  • Checkpoint every quarter: re-take the self-check questions, update this roadmap, and move one level's exit criteria from "planned" to "proved".
  • Stay current: once a month, skim provider security blogs and release notes (AWS, Azure, GCP), the CSA blog, and the accepted papers of one top conference. Add anything durable to the "What's new" section.
  • Get feedback: share threat models and design docs with peers or online communities; principal-level skill is built by having your reasoning challenged.
